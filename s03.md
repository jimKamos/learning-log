## Learned

### TCP — establishes a reliable talk
browser -> server : SYN, start talk, announces its starting sequence number
server -> browser: SYN-ACK, confirms the talk, same to you
browser -> server : ACK, alright let's start talking


Sequence numbers are the whole basis of the reliability — they're how a lost packet gets noticed and resent.

### TLS — asks who is who, and makes the talk private
browser -> server : ClientHello, TLS version, ciphers and hostname
server -> browser: ServerHello, public key certificate
browser -> server : shared symmetric key derived, encryption starts here


Asymmetric crypto (the certificate's key pair) is used once to agree a secret. Everything after is symmetric, which is fast. Slow crypto once, fast crypto forever after.

TLS ≠ SSH. SSH is a separate protocol — that's the GitHub push key, unrelated.

### HTTP message anatomy

Both messages have the same 4 parts. Only the start line differs.

| Part | Request | Response |
|---|---|---|
| Start line | method + path + version → `POST /api/users HTTP/1.1` | version + status + reason → `HTTP/1.1 201 Created` |
| Headers | `Name: value` pairs — Host, Content-Type, Authorization | Content-Type, Location |
| Blank line | marks the end of the headers | same |
| Body | optional data I send | optional data I asked for |

Paths are case-sensitive and need the leading `/`. Domains are not case-sensitive.

### HTTP/2 pseudo-headers

example.com and github.com both came back as `h2`. In HTTP/2 the start line is gone — split into `:method`, `:path`, `:scheme`, `:authority`. `:authority` replaced `Host`. HTTP/2 is binary, so there's no raw text to read.

**example.com document request:** `GET` · `200 OK` · `h2` · `content-type: text/html`

### Methods — the 2 properties

- **Safe** — doesn't change anything on the server. Anyone may fire it whenever.
- **Idempotent** — doing it once has the same result as doing it 5 times.

|  | Idempotent ✔ | Idempotent ✘ |
|---|---|---|
| **Safe ✔** | GET, HEAD, OPTIONS | *(empty)* |
| **Safe ✘** | PUT, DELETE | POST, PATCH |

The empty corner is empty because if a method changes nothing, repeating it can't change the outcome. Safe implies idempotent, not the reverse.

Consequence: never put a destructive action behind `GET`. Prefetchers and crawlers will fire it on their own.

### Status codes in the wild — predicted vs actual

| URL | Predicted | Actual | Why |
|---|---|---|---|
| example.com/banana | 404 | 404 | — |
| github.com/jimKamos/no-such-repo-here | 404 | 404 | — |
| httpbin.org/status/418 | no idea | 418 I'm a teapot | Joke code from a 1998 April Fools spec that got implemented anyway |
| wikipedia.org/wiki/Thispagedoesnotexist | 404 | 301 → 404 | `www.wikipedia.org` is the portal, not an article host. Permanent redirect to `en.wikipedia.org` first, *then* the article lookup fails. I assumed one request; there was never one request. |
| httpbin.org/status/301 | 301 → 404 | 301 → 302 → 200 | httpbin chains deliberately. Each hop is a fresh request — and a fresh DNS/TCP/TLS setup if the origin changes. Redirects are not free. |
| logged-out page needing login | 403 | 302 to login | `401` obliges the server to send `WWW-Authenticate`, which makes browsers show the ugly native login dialog. So `401` is for APIs; HTML navigations get redirected. `403` is for when I *am* logged in and still not allowed. |

The 301 → 302 → 200 chain is the interesting one. `fetch` reports only `200` because it follows redirects silently — `res.status` will never show the chain. `res.redirected` and `res.url` reveal it, but otherwise only the Network panel does. Something that will bite me later in React.
