## Learned

### Preflight triggers on a list, not on risk

`X-Api-Key` on a `GET` preflights. A plain `GET` to a server with no CORS headers at all does not. Nothing about how dangerous the request looks matters — one non-safelisted header is sufficient, and its absence is sufficient the other way.

| Request | Preflight? |
|---|---|
| `GET` httpbin, no custom header | no |
| `GET` httpbin + `X-Api-Key` | yes |
| `GET` my own unprotected server | no |

`Access-Control-Request-Method: GET` proved it — the method was never the reason.

### The browser lowercases the header name

I sent `X-Api-Key`. The `OPTIONS` request declared `x-api-key`. My machine normalised it before sending; httpbin just echoed it back. Same rule as h2/h3 lowercasing every field name (S04).

**Third time case has caught me** — S03 (paths vs domains), S05 (`SHOP.example.com`), now this.

### Cost of a preflight

| Row | Time | Size |
|---|---|---|
| `OPTIONS` preflight | 499 ms | 0.0 kB |
| the real `GET` | 134 ms | 1.1 kB |

The permission check was ~4× slower than the thing it permitted, for an empty body. `Max-Age` is a performance header, not just a correctness one.

### httpbin's own bugs, spotted live

- `Access-Control-Allow-Origin: https://example.com` echoed back, **no `Vary: Origin`** — the exact cache-poisoning risk I wrote down as theory in S05, in the wild.
- `Allow: HEAD, OPTIONS, GET` vs `Access-Control-Allow-Methods: GET, POST, PUT, DELETE, PATCH, OPTIONS`. Different jobs: what the resource does vs what cross-origin permission covers. Permission to *try* `DELETE` isn't a promise it works.

### The read, not the send — watched from both sides

Browser: `net::ERR_FAILED 200 (OK)`, `catch` got `Failed to fetch`.
Server terminal, same moment: `GET /`, handler ran, `200` + full body sent.

Nothing was blocked at the server. The response arrived intact and the browser refused to hand it to my JS. If that had been `POST /delete-account` the account would be gone and the `catch` would still say `Failed to fetch`.

Also: loading `localhost:3000` in the address bar proved nothing — the page was fetching itself, so CORS never applied. Same non-evidence as *"works in Postman"* (S05).
