## Learned

### An origin is a triple

Scheme + host + port. All three must match. Path, query and fragment don't count.

| vs `https://shop.example.com/products` | Verdict | Why |
|---|---|---|
| `https://shop.example.com/cart` | same | path only |
| `http://shop.example.com/products` | different | scheme **and** implied port (443 → 80) |
| `https://shop.example.com:8443/products` | different | port |
| `https://example.com/products` | different | host — subdomains are separate origins |
| `https://SHOP.example.com/products` | **same** | host is case-insensitive |
| `https://shop.example.com:443/products` | same | 443 is the https default |

The port is in invisible ink: `https` = 443, `http` = 80, always present. Why `localhost:3000` and `localhost:5173` are different origins.

### The policy blocks the read, not the send


`ERR_FAILED` and `200 (OK)` on one line — the request ran, the read failed.

- The side effect already happened. A blocked cross-origin `POST /delete-account` still deletes.
- My frontend cannot fix a CORS error. Only the server that owns the resource can.
- Only browsers enforce it — "works in Postman" proves nothing.
- JS gets `TypeError: Failed to fetch`. No status, no reason. **A CORS block and dead wifi are indistinguishable in a `catch` block.**
- The console names the fix: `No 'Access-Control-Allow-Origin' header is present on the requested resource.`

### The permission headers
GET https://www.wikipedia.org/ net::ERR_FAILED 200 (OK)
`Access-Control-Allow-Origin` takes one origin or `*` — never a list. Serving many origins means reading `Origin` and echoing one value back.

`Origin` is the serialised triple: `https://example.com`. No path — sending it would leak `/accounts/GR16...` to a third party.

| `Allow-Origin` | With `Allow-Credentials: true` |
|---|---|
| `*` | **Illegal** — would mean any site may read this *as the logged-in user* |
| one named origin | legal |

Credentials = cookies. A cross-origin `fetch` sends **none** by default, whatever `Domain`/`SameSite` say.

A server echoing `Origin` must send `Vary: Origin`, or a shared cache serves one origin's permission to another (S04).

### The preflight

OPTIONS /orders/42 Access-Control-Request-Method: DELETE
204 No Content Access-Control-Allow-Methods: DELETE
DELETE /orders/42 ← only now is the real request sent


**A refused preflight means the real request is never sent** — no side effect. Simple requests run and are merely unreadable; preflighted ones are genuinely prevented.

Why: a `<form>` could always POST cross-domain, so servers from 2003 expect it. It could never send `DELETE` or JSON. **The preflight protects old servers from new browsers.**

| | Simple | Preflighted |
|---|---|---|
| Method | `GET`, `HEAD`, `POST` | `PUT`, `PATCH`, `DELETE` |
| Headers | safelisted only | any custom (`Authorization`, `X-Api-Key`) |
| `Content-Type` | `text/plain`, form types | `application/json` |

Every real API sends JSON, so **almost everything preflights**. `Access-Control-Request-Headers` only appears when there are custom headers to declare.

### The Max-Age trap

`Max-Age: 3600` caches the permission for an hour, keyed on origin + URL + method + headers. Re-run and the `OPTIONS` row vanishes. So: fix the server, retry, get the same error — because the browser is replaying a cached *refusal*.

Same shape as the S04 hour, opposite fix: there I **unticked** Disable cache to see caching; here I **tick** it to stop a cache hiding my work.
