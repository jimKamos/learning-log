## Learned

### The jobs a header does

| Job | Doing what | Examples |
|---|---|---|
| Negotiation | Client says what it handles, server picks | `Accept-Encoding` |
| Description | Metadata about *this* message's body | `Content-Type`, `Content-Encoding` |
| State | Re-identifying me, since HTTP is stateless | `Cookie`, `Authorization` |
| Instructions | How the other side should behave | `Cache-Control`, `Set-Cookie` |
| Diagnostics | Reports what happened; no RFC, vendor-prefixed | `Cf-Ray` |

Names are case-insensitive; h2/h3 lowercase them all. Colon-prefixed fields (`:method`, `:path`, `:scheme`, `:authority`) are the HTTP/1.1 start line split into fields — seeing them means h2 or h3. Protocol column read **h3** all session.

The loop I watched complete: I sent `Accept-Encoding: gzip, deflate, br, zstd`, server answered `Content-Encoding: br`. Negotiation is the request side, description is the answer.

`q=0.9` is relative preference, 0–1, defaults to 1. `en-US, en;q=0.9, el;q=0.8` = US English, then any English, then Greek.

### Cookies

Not symmetric: `Set-Cookie` is a **response** header, one per cookie. `Cookie` is a **request** header, all of them in one semicolon-separated line, attached automatically.

| Attribute | Note |
|---|---|
| `Max-Age` / `Expires` | Neither → session cookie, dies with the browser |
| `Domain` | Omitting it is *narrower* — exact host only |
| `Secure` | HTTPS only |
| `HttpOnly` | Hidden from `document.cookie` — injected scripts can't steal it |
| `SameSite` | `Strict`/`Lax` (default)/`None`; `None` requires `Secure` |

Sent on **every** matching request, including images and CSS. 4 kB × 60 assets = 240 kB of overhead.

**Predicted vs actual:** I expected `dotcom_user` in `document.cookie`. It was absent. So were `user_session` and `logged_in`. Present: theme, timezone, `cpu_bucket`. **Every cookie JS can see is a display preference; every cookie it can't identifies me.**

Values are percent-encoded — `%2F` = `/`, so `tz=Europe%2FAthens` is `Europe/Athens`. Decode with `decodeURIComponent()`.

### Caching = two different questions

**Freshness is a stopwatch.** Under `max-age`, no request is sent at all. That's the 0 ms hit.
**Revalidation is a question.** Stopwatch expired → conditional request → `304 Not Modified` with **no body**, and the stopwatch resets on the copy already stored.

| Directive | Note |
|---|---|
| `max-age=3600` | Seconds, not ms |
| `no-cache` | Store it, revalidate before each use. **Does not mean don't cache** |
| `no-store` | This is what `no-cache` sounds like |
| `private` | Browser only — blocks CDNs. Use for user-specific responses |
| `s-maxage` | Separate max-age for shared caches |
| `immutable` | Only safe with a content hash in the filename |

Validators: `ETag` ↔ `If-None-Match`, `Last-Modified` ↔ `If-Modified-Since`. ETag is a hash meaning "this exact version"; it wins if both are present. `Vary` tells a cache which *request* headers are part of the key.

### The two real examples

`Cf-Cache-Status: HIT` + `Age: 5608` — Cloudflare's Athens edge served a 93-minute-old copy without asking the origin. `Age` is the cache reporting its own stopwatch. That's S03's DNS resolution made visible.

`primer-tailwind-compatible-330c475bd59f66d2.css` → `public, max-age=31536000, immutable`, no ETag. 365 days, and the hash in the filename is *why*: change the CSS, the URL changes, so a URL can never mean two things. Revalidation is impossible to need, so an ETag would be dead weight — its absence is correct.
